## 1. Паспорт приложения

**Название в Marketplace (display_name): «Keragon»**. Внутренний
app_id/папка: `keragon-connector`.

**Keragon Connector** — двусторонний webhook-мост между Imperal и
Keragon (не полноценный CRUD-коннектор — см. CONNECTOR_DISCOVERY.md §3
за архитектурным обоснованием, тот же класс ограничения, что у Zapier
Webhook):

- **Исходящее направление (Imperal → Keragon):** запуск конкретного
  Keragon-workflow отправкой HTTP POST на его "HTTP Webhook Trigger"
  URL. Поддерживает множественные именованные мосты (не один анонимный
  URL, как у Zapier Webhook) с описанием/меткой на каждый.
- **Входящее направление (Keragon → Imperal):** приём HTTP-запроса,
  который шаг "HTTP Client action" внутри workflow Keragon шлёт на наш
  webhook URL, с ротируемым общим секретом в заголовке.
- **Ярус 3 value-add:** bulk-рассылка одного события сразу на несколько
  исходящих мостов, свободная таксономия `event_kind` на входящем логе,
  агрегирующий health-отчёт по мостам (сколько настроено, сколько
  событий получено, есть ли "тихие" мосты без единой доставки).

BYOK: нет привычного API-ключа (Keragon не выдаёт его для этой модели) —
пользователь сам создаёт триггер/экшен внутри СВОИХ workflow в Keragon
UI и вставляет полученные/сгенерированные URL сюда. Imperal ничего не
хостит и не проксирует, кроме самого HTTP-запроса.

## 2. Ключевые архитектурные решения

1. **Не CRUD-коннектор.** Нет `list_workflows`/`run_workflow`/
   `list_executions` — Keragon этого не даёт стороннему клиенту.
   Подтверждено многократным целевым поиском (см. Discovery §2).
2. **Множественные именованные мосты**, а не единственный URL (в отличие
   от Zapier Webhook, где ровно один исходящий + один входящий канал).
   Обоснование: Keragon-клиенты реалистично держат несколько параллельных
   healthcare-workflow (intake, reminders, insurance verification,
   no-show recovery) — один общий URL резал бы функциональность вдвое
   против того, что архитектура сервиса реально позволяет.
3. **Общая коллекция `keragon_bridges`** (`ctx.store`) хранит метаданные
   моста (id, name, direction, description, created_at); сам секретный
   URL — в `ctx.secrets`, ключ `keragon_bridge_url_{bridge_id}`, не в
   сторе (следуя тому же разделению "секрет vs метаданные", что и во
   всех остальных коннекторах платформы).
4. **Один общий входящий webhook-путь** (`/inbound`), различающий мосты
   по `bridge_id` в query string (`?bridge=<id>`), а не отдельный путь на
   каждый мост — `@ext.webhook` регистрирует путь статически при
   декларации, поэтому per-bridge пути потребовали бы динамической
   регистрации, которой SDK не даёт. Query-параметр — рабочий эквивалент.
5. **HMAC `compare_digest`** на проверке входящего секрета (не голый
   `==`) — тот же стандарт, что в Zapier Webhook/Make.com Connector.
6. **Официальный SVG-логотип** — `icon.svg` взят с `keragon.com/brand`
   (синий квадрат 800×800, `#0066FF`, фирменный "два треугольника"
   символ) — единственный реально доступный векторный ассет с того
   сайта (полный текстовый логотип с надписью тоже найден и хранится не
   используется, т.к. квадратная марка лучше подходит под формат иконки
   приложения, как и в остальных коннекторах портфеля).

## 3. Объём релиза

Ярус 1 (обязательный) + Ярус 2 (полное покрытие) + Ярус 3 (наш
value-add) — всё включено в этот единственный заход, по прямому
указанию пользователя. Полный список функций — см.
`CONNECTOR_DISCOVERY.md` §2.

## 4. UI

Один "App settings" во внешнем сайдбар-слоте (`keragon_center` panel),
центр-слот `keragon_settings` (`panels_settings.py`) со всей
конфигурацией: список исходящих мостов (создать/удалить), входящий
секрет (сгенерировать/ротировать), последние входящие события. Следует
`UI_INTERFACE_STANDARD.md`: полноширинные формы, лейблы на каждом поле,
инструкции только в модалке помощи, не дублируются в сайдбаре.
